# Memory curation: an anonymized worked example

## How to read this example

This example is adapted from a reviewed project-memory cleanup. Project names, people, task and candidate identifiers, dates, internal paths and exact operational allowances are omitted or replaced. The excerpts are teaching adaptations, not verbatim source quotations or fresh test evidence. The original project evidence remains with its owner and is not included here.

The decisions illustrate the method. They do not establish another project's engine policy, temporary-path limit, runtime readiness or permission to run tests. File names in the excerpts are illustrative routes inside an example project, not files bundled with this skill.

## 1. Separate a review receipt from knowledge

The old index repeatedly contained Latest/Prior review blocks reporting no new memory candidates, listing task outcomes and recording that a broad topic remained unchanged. An adapted excerpt:

```text

retained delivery and independent verification. No new memory candidates.

```

That receipt belongs to the existing task/decision, not active memory. Removing it from the index does not erase the review or its adverse evidence. Do not replace the index log with another always-growing maintenance log.

This is not a complete topic inventory or a target index length.

## 2. Split different triggers; retain a usable fact

An old paragraph mixed a Bee socket-path failure with minimal Unity project/module bootstrapping. These solve different problems and became separate topics. The adapted Bee topic below retains the workaround and its evidence boundary without promoting a script guard into a universal operating-system limit.

```markdown
---
name: bee-short-temporary-path
description: "Diagnose the observed Bee socket-path failure and reuse its checked short engine-only temporary path."
metadata:
  type: project
---

## Context

An initial Unity import failed because a long task-run temporary directory made Bee Unix-domain socket paths exceed the host limit. A dedicated short `.unity-tmp/` path resolved that recorded failure. The retained candidate script also checked a concrete path-length limit; that guard applies to the script, not universally to macOS.

## Why

A valid Unity installation can still fail during import because of its execution path. The diagnosed cause and bounded workaround remain useful for later imports in the same project.

## How to apply

When an authorized import/build log shows this socket-path failure, inspect the actual path and reuse the checked short-path script. Read the retained script for its exact length guard and applicable environment before reuse.

Use run scratch for ordinary temporary output. The short project directory is an engine-IPC exception, not a new general output location. Diagnose later errors from their actual logs rather than assuming every build failure has this cause.

## Evidence

- [Retained import failure and workaround](../evidence/import-path-probe.md), including the checked script and independent verification references.
- [Formal engine decision](../decisions/engine-selection.md). The historical workaround is not fresh build qualification.
```

The evidence paths above are illustrative replacements, relative to the example project's `docs/memory/bee-short-temporary-path.md`. They are not public evidence links and must not be copied into a real store as if they resolve. In an actual curation, retain the source's exact relevant limit and use real canonical evidence routes; values were withheld here for publication, not discarded from the real memory.

## 3. Merge a failed assumption and its bounded correction

Two clock sections answered one future question: which clock domain can external QA compare?

- An earlier assessment observed different origins for Python monotonic time and Swift system uptime. A defective deadline branch remained unexecuted because an earlier release guard stopped the assessment.
- A later probe measured a shared `mach_continuous_time` domain for its recorded host/runtime combination.

They became one `cross-process-qa-clock-domains.md`. It retains the measured counterexample, later method, conversion and applicable environment. It also preserves that no OS Quit or sleep/wake experiment occurred and the candidate remained NOT READY because release-state flags were unresolved. A corrected clock method is not lifecycle acceptance or permission for a new runtime experiment.

## 4. Correct obsolete applicability, not historical evidence

An old broad topic described an early grayscale, bilinear and runtime-tint contract. Later owner direction explicitly approved prospective pixel-art/UI supersession; the accepted new asset contract supplied its own full-colour/Point scope.

The current sprite topic therefore:

- Keeps old candidate evidence historical rather than pretending it was always wrong.
- Routes new work to the applicable current art/integration contract.
- Does not claim that accepted source/static exports were installed or runtime-accepted.
- Retains that a later validator closed a specific early coverage gap for its candidate, while future changed candidates still need readback.
- Preserves actual source/export hashes and generation/edit provenance, without relabelling authored pixel work as generated.

The formal owner direction, art specification and candidate integration contract remain authoritative. Memory does not duplicate their palette/asset tables.

## 5. Retire the catch-all without breaking readers

The old multi-topic file leaves active memory only after new topics and reading routes exist. In the source cleanup, an already-retained, byte-identical frozen source could serve historical citations; a new permanent memory-history archive was unnecessary. Active readers instead follow the current index and relevant topics.

Updating files and evidence routes does not replay historical probes, change operation budgets or prove that a newly resumed agent has read the revised store.

## Questions to use in a review

- Is the Bee length guard a universal macOS constant? **No; it is bound to the recorded script.**
- Must new pixel work inherit old grayscale/bilinear defaults? **No; follow explicit supersession and the applicable contract.**
- Does the measured clock method prove a successful Quit? **No; preserve the unexecuted/NOT READY qualifications.**
- Does a no-candidate review force a file edit? **No; return reviewed/no-change through the existing reporting mechanism.**

These questions illustrate the expected interpretation, not an executed compliance test for every future worker.
