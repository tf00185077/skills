# 可信測試系統 · review-gate 設計 spec

- 日期:2026-07-27
- 本輪聚焦:**review-gate**(四件式系統中的一件)
- 狀態:設計定案,待落實為 skill

---

## 1. 背景與問題

讓 agent 寫完 code 後,測試可靠到「在覆蓋範圍內,使用者不用人工測也能有把握沒問題」。

實務上最大的障礙不是「測試不夠多」,而是 **測試綠燈 ≠ 行為正確**。觀察到的三個根因:

1. **Mock 與真實不符** — 依賴被 mock 掉,mock 行為與真實不同;測試綠,串真實依賴就爆。
2. **agent 測自己的實作** — 邊寫邊測,測試只把「目前行為」釘住,而非「正確行為」;spec 被自己誤解。
3. **邊界/整合沒測到** — 單元全綠,但模組接縫、資料流、非快樂路徑沒人測,實際使用爆在這裡。

三者同屬一個家族:**測試沒有反映真實 / 測到錯的東西**。

另一個張力:**全上 E2E 成本太高,層級邊界難取捨。**

## 2. 核心洞察

> 要的不是「更多測試」,而是「**證明測試沒說謊**」。信心的來源要從『測試過了』改成『我有證據證明這些測試真的會抓到 bug』。

## 3. 全系統概觀(四件式)

本 spec 只實作 review-gate,但它依賴其餘三件,先定義關係以免各自漂移。

```
                    ┌──────────────────────────────────┐
                    │  共用核心 (shared)                 │
                    │  · 可信測試判準 (無假綠燈的定義)     │
                    │  · 交棒契約 (spec 格式 / 宣稱清單格式)│
                    │  · 風險分層規則 (意圖→層級→查核深度) │
                    └──────────────────────────────────┘
                         ▲          ▲          ▲
              引用判準+格式 │          │          │ 引用判準+格式
                    ┌──────┴───┐ ┌───┴────┐ ┌───┴─────────┐
                    │ spec-    │ │coding  │ │ review-gate  │  ◀── 本輪
                    │ authoring│ │        │ │              │
                    └────┬─────┘ └───┬────┘ └──────┬───────┘
                         │ spec       │ 宣稱清單     │ 讀 spec 不讀答案卷
                         └───────────▶├───────────▶│
                                      ◀── 缺口打回 ──┘
```

| 角色 | 給誰 | 職責 |
|---|---|---|
| **spec-authoring** | 寫 spec 的 agent | 從請求草擬**意圖導向、最小化**的 spec;只在真正有歧義處和人「對答案」 |
| **coding** | coding agent | 依 spec 推導義務、依風險分層規則決定層級、關鍵邊界不 mock、產出宣稱清單 |
| **review-gate** | review agent | 依 spec **獨立**推導攻擊、破壞驗證、邊界稽查、輸出過/不過+缺口 |
| **共用核心** | 三者引用 | 可信測試判準 + 交棒契約 + 風險分層規則(把三件綁成一致系統的那條線) |

**作者中立**:spec 由 agent 撰寫,只在需要處和人對答案;至於是第三個 agent 還是 coding agent 確認需求後寫,skill 不綁死,只規範 spec 的品質標準。

## 4. 全系統共通原則

### 4.1 內部正確 vs 外部正確(gate 的邊界)

- ✅ **內部正確(gate 負責)**:code 確實做到 spec 說的事,且測試真的在驗證這件事(無假綠燈)。
- ❌ **外部正確(人類負責)**:spec 本身對不對、合不合使用者真意。**這一圈故意不由 agent 關閉**,由使用者實際用、測出不對,才開下一輪修改。

理由:人類過多限制反而稀釋 agent 能力;把「意圖對不對」交回人類、用使用來驗證,比讓人先釘死一堆條件更好,也避免 agent「為過關而寫測驗/改邏輯」。

### 4.2 spec 的定位

spec 描述**意圖與可觀察結果**,盡量最小、**不釘實作、不指定測試方法**。spec 唯一的額外義務:讓每條意圖的**風險屬性**可判定(看不看得見、碰不碰金流/資料遺失/安全/核心承諾)。

### 4.3 測試層級不是判斷,是推導

「要不要 E2E」不是意見,而是由共用核心的**風險分層規則**從意圖的風險屬性推導。兩個 agent 對同一 spec 套同一規則 → 得同一答案。分歧化約為「風險屬性的事實認定」,可被規則裁決;真的無法判定,代表 spec 沒講清楚 → 走 spec 澄清,不在 coding-review 間迴圈。

## 5. review-gate 詳細設計

### 5.1 觸發與輸入

coding agent 交出成果後啟動。輸入:

1. 共享 spec(意圖與可觀察結果、風險屬性)
2. production code
3. 測試碼
4. 宣稱清單(每個行為 → 哪層測試 → 跑在什麼真實環境)
5. 執行權(能跑測試、能暫時改壞 code 再還原、能跑 E2E)

### 5.2 兩條鐵則

- **獨立性鐵則**:review agent **先讀 spec、自己列出「哪些可觀察行為必須成立」當答案卷,之後才准看 coding agent 的測試。** 稽核對象是「意圖 vs 成果」,不是「coding 的測試 vs coding 的 code」。順序不可顛倒。
- **防污染鐵則**:review agent **只讀、只攻擊、只報告,絕不修改 production 邏輯讓它過關。** 唯一能改的是「為破壞驗證暫時植入、事後立即還原」的東西。

### 5.3 五道查核(依序,前面攔到嚴重缺口可提早回報)

**① 獨立列答案卷(intent 抽取)**
讀 spec,自己寫出「必須成立的可觀察行為」清單,每條標風險層級。此時**不准看 coding 的測試**。

**② 意圖覆蓋對照(intent coverage,非 code coverage %)**
①的每條意圖對照「有沒有測試在驗、在哪層」。對不到 → 缺口。刻意不看覆蓋率數字,避開 Goodhart 陷阱。

**③ 破壞驗證(gate 的牙齒,核心)**
對每條意圖(Critical 必做,Peripheral 抽樣):
```
1. 在 production code 植入「最小的、應違反這條意圖」的改動 (targeted mutation)
2. 跑測試
3. 預期:至少一個測試變紅,且變紅的是語意上對應這條意圖的那個測試
4. 若測試全綠 → 這條意圖是假綠燈 → 記為缺口
5. 還原改動
```
例:意圖「金額為負要擋下」。把 `if (amount < 0)` 改成 `if (false)`,跑測試;無測試變紅 → 「擋負數」沒被真正驗證。

這是**針對意圖的定點 mutation**(非全域窮舉),便宜且有意義,一次打掉「測自己的實作 / 空測試 / 為過關而寫」。

**④ 邊界真實性稽核**
宣稱清單標「對真實邊界驗證」的行為,實際檢查測試有沒有接觸真東西。宣稱對真實 API 卻打在 mock 上 → 缺口。打「mock 與真實不符」。

**⑤ 環境真實性檢查**
關鍵、使用者看得見的路徑,其 E2E 是否跑在**擬真環境**(真瀏覽器/真建置)而非 jsdom stub。這是「E2E 真的有覆蓋」的前提。

### 5.4 風險分層(決定查核深度,解決成本/邊界取捨)

| 層級 | 判定 | gate 要求 |
|---|---|---|
| **Critical** | 使用者看得見 **且** 涉及金流/資料遺失/安全/核心承諾 | E2E 或整合**接觸真實邊界** + **破壞驗證必做且必須存活** |
| **Core** | 重要邏輯,壞了影響功能但非災難 | 整合/單元(邊界處用真依賴)+ 破壞驗證 |
| **Peripheral** | 外觀、罕見路徑 | 單元即可,破壞驗證抽樣 |

**關鍵**:E2E 只保留給 Critical 的使用者可見意圖(成本可控);其他層靠「破壞驗證存不存活」買信心。**不是用測試層級買信心,而是用破壞驗證買信心** → 不必全上 E2E 也可靠。

此表(意圖風險屬性 → 層級 → 深度)是**共用核心**的規則,coding 與 review-gate 共用同一份。

### 5.5 三態判定

| 判定 | 意思 | 去向 |
|---|---|---|
| **PASS** | 每條 spec 意圖都被驗證且破壞驗證存活 | 完成(附「未涵蓋清單」) |
| **FAIL(內部缺陷)** | spec 明列意圖沒被真正驗證(破壞存活 / 邊界偷 mock) | 打回 coding agent — 客觀無爭議 |
| **SPEC 歧義** | 分歧源於 spec 沒講清楚「X 要不要」 | **不打回 coding**,升級 spec 澄清(和人對答案) |

三態的意義:把「SPEC 歧義」從「FAIL」拆出來,避免把歧義一直丟回 coding 造成**永遠過不了 review**。歧義走 spec 澄清(外部正確 = 人類職責),不在 coding-review 間拉扯。

### 5.6 防假陽性與防迴圈

- **規則 1 — 不審「怎麼測」,只審「意圖有沒有被真的驗證」**:明文禁止「我會用別的方式測 / 這該用 E2E」這類**風格性**否決。方法不同但意圖被驗證 → 過。
- **規則 2 — 每條缺口必須「引用 spec 具體意圖」+「附客觀證據」**:證據只有兩種算數:①破壞 spec 明列行為後測試全綠(存活);②宣稱真實邊界卻是 mock。**引用不到 spec 意圖的發現一律不成立**。破壞驗證是客觀的,無風格爭論空間。
- **申訴權**:coding agent 可對 finding 回「這不在 spec」。一旦被申訴、或**同一 finding 跨輪重複**,自動升級為「SPEC 歧義」送澄清,**不准原地再丟回一次**。(呼應 receiving-code-review:收到審查要驗證,不盲從。)

### 5.7 PASS 必附「未涵蓋清單」

PASS 只代表「**這些**意圖內部正確」,不等於「整個東西對」。PASS 一定要明列:

- 已驗證涵蓋的意圖(可安心免人工測的範圍)
- 未涵蓋 / 刻意不驗的部分(使用者仍需自己確認的殘餘面)

## 6. review-gate 對共用核心的依賴(本輪需先定義的最小介面)

review-gate 無法獨立運作,依賴共用核心提供:

1. **可信測試判準** — 「無假綠燈」的正式定義(破壞驗證存活、邊界不得偷 mock、意圖須被覆蓋)。
2. **交棒契約 · spec 格式** — 意圖 + 可觀察結果 + **每條意圖的風險屬性欄位**(看不看得見 / 碰不碰金流·資料·安全·核心承諾)。
3. **交棒契約 · 宣稱清單格式** — 每個行為 → 測試層 → 真實環境 → (coding 自評的)風險層級。
4. **風險分層規則** — 5.4 那張表,雙方共用。

> 本輪實作 review-gate 時,需同步把上述 4 項在共用核心裡定義到「review-gate 夠用」的最小程度;完整版留待 coding / spec-authoring 兩輪再補。

## 7. 不在本 spec 範圍

- spec-authoring、coding 兩個 skill 的完整設計(之後各自一輪)。
- 綁定特定工具鏈(本系統為通用、跨專案,只給原則與可驗證步驟,不寫死 Vitest/Playwright 等)。
- 外部正確(spec 是否符合使用者真意)的自動判斷 — 明確交給人類。

## 8. 待後續釐清 / 可能修改

- 破壞驗證在無 mutation 工具的專案裡,由 agent 手動定點植入的**操作規範**細節(如何選「最小改動」、如何確認「變紅的是對的測試」)。
- 「未涵蓋清單」呈現給使用者的具體格式。
- 申訴/升級的回合上限具體數字。
- 共用核心四項介面的正式 schema(本輪先給最小可用版)。

> 採此設計,發現不足再修改。
